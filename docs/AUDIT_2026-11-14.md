# Аудит V2 перед публикацией — 14.11.2026

Проверены исходники V2, авторизация, изоляция групп, очереди, модельный адаптер, миграции, эксплуатационные инструменты и публичная документация. Аудит выполнялся локально: production не обновлялся, его БД и действующая связка не изменялись. Это инженерная проверка с тестами, а не гарантия отсутствия всех ошибок и не заключение о текущей доступности Telegram.

## Найдено и исправлено

| Проблема | Последствие до исправления | Исправление и проверка |
| --- | --- | --- |
| Повторная проверка инцидента не отменяла ещё не отправленные действия | Если повторную проверку запросили во время проверки Telegram-прав, старое удаление могло пройти по прежнему вердикту | Повторная проверка отменяет planned-действия; исполнитель повторно сверяет версию инцидента под блокировкой перед отправкой. Три сценария в `test_dispatch_revision.py` |
| Старт требовал хотя бы одну подключённую группу | После намеренного отключения всех групп перезапуск блокировал личное меню и повторное подключение | Сохранены проверки схемы, подтверждённого импорта и владельца; отсутствие активных групп допускается. `test_readiness.py` |
| Предрелизная диагностика не сверяла bot ID с импортом | Проверка могла пройти с токеном другого бота, хотя runtime затем отказался бы запускаться | Runtime и preflight используют общую проверку идентичности. Неподтверждённый импорт и чужой bot ID отвергаются |
| Неверная команда запуска health-сервиса | Чистый Linux-запуск завершался `ModuleNotFoundError` вместо диагностики | Systemd запускает `python -m ops.health`; тест выполняет аргументы из настоящего unit-файла без PYTHONPATH и секретов |
| Локальные скриншоты не были исключены из Git | Неосторожное добавление всех файлов могло опубликовать изображения переписки | `.codex-attachments/` и прежний локальный документ планирования добавлены в `.gitignore`; публикация готовится по явному списку |
| README и часть статуса описывали старые сценарии | Ошибочные ожидания: заявки только от владельца, подтверждение каждого вайтлиста, бюджет среди общих настроек | README и текущий статус переписаны под реализованный интерфейс; исторические отчёты отделены от актуальных результатов |

Из одной тестовой фикстуры также убран ID реального тестового бота: проверка использует синтетический большой ID с теми же свойствами.

Исправления аудита не требуют новой миграции схемы и не переписывают существующие историю, страйки, баны или доверие. Состояние `in_flight` не маскируется под отменённое: уже отправленное действие Telegram мог выполнить.

## Проверенные области

- **Доступ:** группа, актуальная привязка, роль и членство; персональные подтверждения с ограничением срока и версии. Финансы требуют владельца и личного чата, включая прямое обращение к обработчику.
- **Сохранность:** импорт локализует прежнее доверие в основной группе; прочие группы сохраняются архивными. Повторный импорт не восстанавливает отозванное доверие. Отключение и перенос не удаляют историю.
- **Доверие и решения:** изоляция A/B, настройка порога, новый цикл после отзыва/истечения, идемпотентность, альбомы/правки, исправление конкретного случая без массового сброса страйков.
- **Исполнение:** версии политики/привязки/инцидента, потеря роли, пауза, неизвестные результаты, защита от повторных наказаний, отдельные разбан и размут. Намерение и результат Telegram записываются раздельно.
- **Модель и контент:** структурированный ответ, лимиты текста/OCR, ошибки провайдера и 429, параллельность, резервирование расхода. Ошибка не превращается в безопасный результат и не начисляет доверие.
- **Эксплуатация:** изолированные тестовые БД, snapshot бэкапа, сохранение предыдущих копий при ошибке dump, ротация, проверка восстановления и карантин восстановленной очереди.
- **Интерфейс:** общая лента и контекст кнопок, скрытые финансы, поиск без обязательного ID и ручной ввод, длина callback/сообщений, упоминание автора и формат даты.

## Фактические результаты

- **150 тестов прошли** в Linux/Python 3.12 с отдельной PostgreSQL-БД. Единственное предупреждение — невозможность записать pytest-cache в read-only mount; оно не относится к приложению.
- `ruff check` и `ruff format --check` прошли для 70 файлов проверяемого кода, тестов и инструментов.
- `pip check` не обнаружил конфликтов зависимостей. Проверены 112 файлов публикации: совпадений с локальными секретами, шаблонами API-ключей и выбранными боевыми идентификаторами не найдено; закрытые документы, дампы и изображения исключены из Git.
- `pip-audit` для runtime requirements: известных уязвимостей на момент запроса не найдено. Это проверка опубликованной базы уязвимостей, а не доказательство безопасности будущих версий.
- Повторная миграция исходного архива на новой локальной БД до схемы `0007_group_requests`: сохранность исходных полей подтверждена; искусственный сбой откатился целиком; повторный импорт сохранил отзыв доверия. SHA-256 оригинального архива до/после совпал. Telegram/OpenAI не вызывались.
- Ранее в этой работе выполнены dump/restore и карантин на отдельной копии тестовой V2-БД со сверкой 38 таблиц; ротация и ошибки создания бэкапа дополнительно входят в текущие автотесты.
- Зафиксированные SHA GitHub Actions сверены с соответствующими тегами upstream. Результат удалённого CI следует проверять по фактическому коммиту после push; локальный прогон его не подменяет.

## Остаточные ограничения и приоритеты

1. **До переключения VPS:** новый дамп, повторная сверка миграции, актуальная карта связки/ролей, проверка окружения и восстановление. Репетиция на ранее полученном архиве не покрывает новые сообщения после его создания.
2. **До эксплуатации бэкапов:** установить timer, проверить свежесть и аварийное уведомление на VPS. Согласованная ротация — семь ежедневных копий; потерю диска VPS она не покрывает.
3. **До смены модели:** независимая оценка качества и стоимости. Тестовые карточки подтверждают интеграцию, а не приемлемый процент ложных блокировок.
4. **После переключения:** контроль первой связки минимум сутки. Дополнительные живые проверки переноса админки/другого администратора сняты владельцем; это не означает, что они пройдены в Telegram.

Новых блокирующих дефектов в проверенных сценариях после исправлений не выявлено. Следующий этап — публикация проверенного кода, затем отдельная подготовка производственного переключения по [плану](IMPLEMENTATION_STATUS.md).
