# Развёртывание и восстановление V2

Шаблоны в этом каталоге не устанавливаются автоматически. Производственное переключение выполняется в согласованное окно после выполнения выпускных проверок. Не запускать старый и новый receiver одновременно с одним Telegram-токеном.

## Выпускные условия

1. Проверенная свежая копия БД, архив старого кода и конфигурации; конфигурация хранится отдельно с ограниченным доступом. Получить фактическую действующую админскую группу, владельца и состав модераторов. Не угадывать их по старым callback или тестовым группам.
2. Репетиция миграции на копии с отчётом сохранности и повторного запуска. Подготовить `migration.json` по схеме `app.v2.migration.Manifest`: bot ID, primary IDs, явные source/archived группы, owner IDs, локальные роли, полная политика, SHA-256 соответствующего архива, `purpose`.
3. Linux, Python 3.12, актуальный PostgreSQL 17, Tesseract с `rus`, `ukr`, `eng`. Предрелизный инструмент требует PostgreSQL не старее 17.12; перед развёртыванием дополнительно проверить актуальность исправлений. Локальная проверка на 17.9 не закрывает этот пункт.
4. Тестовый Telegram-бот и две пары групп: реальный мастер, фактические права, роли, ограничения, удаление, тихие часы, потеря прав и повторный запуск. История production в тестовые группы не публикуется.
5. Локальные бэкапы на VPS: ежедневно, последние семь успешных плановых копий, отдельная копия перед обновлением. Проверить восстановление в пустую БД. По решению владельца облако и внешнее хранилище не требуются. При исправном расписании возможна потеря изменений за последние сутки; потеря диска VPS не покрывается этим режимом. Прежний RPO 15 минут отменён; время восстановления измеряется при репетиции.
6. Независимый монитор missing-heartbeat с проверенным аварийным каналом. Остановка самого бота не должна отключать мониторинг.
7. Смена модели отделена от выпуска V2. Независимая разметка, контрольный набор, фактические API-параметры/доступность/расход и критерии качества проверяются до изменения `OPENAI_MODEL`.

Уточнение владельца от 14.11.2026 к пункту 4: дополнительные ручные проверки переноса админки и работы с другим администратором опущены. Для этих сценариев основанием служат проверка кода и автотесты; двух существующих тестовых пар достаточно. Остальные условия выпуска действуют.

## Подготовка сервиса

- Создать непривилегированного пользователя `antiscam`, каталог релизов `/opt/antiscam-bot/releases/<release>`, ссылку `/opt/antiscam-bot/current`, конфигурацию `/etc/antiscam` и состояние `/var/lib/antiscam`.
- Код и `.venv` принадлежат установщику и доступны сервису только для чтения. Конфигурация секретов доступна сервису для чтения. Для локального режима age/rclone и отдельный ключ не нужны; каталог бэкапов закрыт для других пользователей, файлы создаются с правами 0600.
- Установить зависимости из зафиксированных requirements, PostgreSQL client 17, Tesseract и три языка. Не обновлять ОС или PostgreSQL одновременно с непрорепетированным переключением приложения.
- Runtime-роль PostgreSQL: CONNECT, USAGE нужной схемы, DML нужных таблиц и USAGE/SELECT последовательностей; без SUPERUSER, CREATEDB и CREATE схемы. Миграции выполняет отдельная роль владельца объектов.
- Backup-роль имеет чтение всех таблиц/последовательностей этой БД и право экспорта snapshot. Health-роль имеет SELECT `system_state`, `jobs`. Credentials размещаются в файлах, не в аргументах процесса или Git.
- Для PostgreSQL service использовать `pg_service.conf` без пароля и отдельный `pgpass` с режимом 0600. Runtime DSN находится в `bot.env`. В согласованном локальном режиме `BACKUP_REMOTE` не задан.
- Использовать шаблон `ai-antiscam-bot.service`; подготовить все пути, владельцев и права до его установки. Проверить `systemd-analyze verify`. Ограничение памяти 768M — исходный предел, его пригодность подтверждается на целевом VPS вместе с PostgreSQL и OCR.
- Настроить ограниченную ротацию журналов: 14 дней и установленный предел места. Не включать SQL echo, логирование полных updates, промптов, ответов провайдера и DSN. Исходные payload завершённых updates очищаются через 7 дней; receipt для защиты от повторов сохраняется. История модерации автоматически не удаляется.

## Переключение первой связки

Последовательность состоит из отдельных проверяемых шагов. После каждого сохранить вывод без секретов в локальный боевой ранбук.

1. Зафиксировать состояние старого сервиса, число групп/участников/сообщений, множества доверия и балансы. Проверить текущие права Telegram чтением.
2. Остановить старый receiver; убедиться, что его PID завершился. Не сбрасывать очередь Telegram и не использовать `drop_pending_updates`.
3. Сделать отдельный согласованный custom dump перед обновлением и проверить его чтение, контрольную сумму и восстановление. Сохранить отдельно от ежедневной ротации. Пересоздать manifest именно для этой копии; старый исследовательский manifest не заменяет текущие данные.
4. Восстановить в отдельную целевую БД PostgreSQL 17, сохраняя прежнюю БД для возврата до первого V2-события. Не удалять старую БД и код.
5. Установить `ANTISCAM_MIGRATION_DATABASE_URL` из защищённой конфигурации; выполнить предварительное чтение, `alembic upgrade head`, импорт с `--apply`. Команды приведены в `docs/DEVELOPMENT.md`. Не включать DEBUG/echo.
6. Сверить исходные поля, PK, множества доверия, балансы, историю, прогресс и архивные группы. Импорт не выполняет Telegram-санкций. Проверить повтор того же manifest: нет новых выдач доверия или повторного начисления балансов.
7. Выполнить `python -m app.v2.preflight --telegram` от `antiscam`. Проверить отсутствие webhook и права двух групп. Сверить выведенный bot ID с manifest, владельца и роли, фактические runtime-настройки с `primary_policy`. При запуске receiver дополнительно откажется работать с bot ID, отличающимся от импортированного manifest.
8. Включить только V2-сервис с прежней одобренной моделью. Проверить единственный receiver, доставку карточки в существующую админку, доступ прежней команды, обработку новых событий и отсутствие действий в архивных группах.
9. Включить backup/health timers после самостоятельного успешного запуска обеих служб и теста независимого уведомления. Проверить их статус и следующий запуск.
10. Минимум 24 часа наблюдать первую связку. Вторую подключать мастером только после сверки и отсутствия критических ошибок. Начальный режим новой пары — наблюдение; автоматическую модерацию включать явно.

После появления новых данных V2 нельзя просто запустить старый код: он не знает локальных списков и новых решений. При неисправности сначала системная пауза/остановка автоматических действий, сохранение текущей БД и исправление V2. Возврат к старой БД возможен только с отдельным планом переноса накопленных новых событий и решений; бесшумная потеря этого интервала запрещена.

## Backup

`python -m ops.backup` использует Linux lock, согласованный экспортированный snapshot PostgreSQL, custom dump, SHA-256 и построчный manifest из того же snapshot. По умолчанию сохраняет обычные `.dump` и `.dump.json` в `/var/lib/antiscam/backups`, проверяет чтение `pg_restore --list` и только после успеха запускает ротацию. Не требует Telegram, модели, облака или ключа шифрования. Настройки: `backup.env.example`.

Timer запускается ежедневно в 03:00 UTC; `Persistent=true` догоняет пропущенный запуск после включения сервера. `BACKUP_KEEP_COUNT=7` хранит последние семь успешных плановых копий. Health проверяет наличие файла и возраст снимка: по умолчанию 26 часов (`BACKUP_MAX_AGE_SECONDS=93600`, сутки плюс два часа допуска). Ошибка создания/проверки не удаляет прежние копии и не обновляет отметку успеха.

Для очереди предупреждение владельцу начинается при ожидании готового задания от 60 секунд, критический сигнал — от 300 секунд; независимый health-процесс также считает пять минут критической задержкой. Отдельный предел 15 минут для автоматических санкций не используется как порог раннего оповещения. Проверка выполняется раз в минуту; предупреждения одного уровня дедуплицируются в пределах часа, повышение уровня создаёт отдельное уведомление.

Перед обновлением выполнить `python -m ops.backup --before-update` с тем же защищённым окружением. Копии `preupdate-YYYYMMDDTHHMMSSZ.dump` не удаляются ежедневной ротацией; убрать их можно отдельно после приёмки обновления. Ротация касается только завершённых пар `antiscam-YYYYMMDDTHHMMSSZ.dump` и соответствующего manifest. Чужие файлы, старые `.dump.age`, незавершённые копии и symlink не удаляются. При необходимости ручные дополнительные плановые запуски тоже входят в последние семь.

Прежний режим age+rclone сохранён как необязательный: включается только явным `BACKUP_REMOTE` и требует `AGE_RECIPIENT`. Для согласованного варианта эти переменные оставлять незаданными. Внешнее хранилище не является выпускным условием.

## Проверка восстановления

Перед значительным выпуском и периодически проверять локальные `.dump` и `.dump.json` в отдельной пустой БД `antiscam_restore_*`; инструмент откажется перезаписывать непустую БД. Указать её защищённый DSN в `ANTISCAM_RESTORE_DATABASE_URL`.

```sh
.venv/bin/python -m ops.restore_drill /private/backup.dump /private/backup.dump.json \
  --output /private/restore-report.json
```

Инструмент проверяет SHA-256, восстанавливает в одной транзакции, сравнивает количество и хеш строк каждой таблицы, проверяет ограничения и последовательности. Для старых age-архивов также поддерживается `--identity`. Отчёт включает длительность, но полный срок восстановления включает обнаружение сбоя, подготовку и сверку Telegram. Локальная ротация не обещает восстановление после потери диска VPS.

Проверка последовательностей исключает только четыре явно назначаемых ключа: Telegram ID в polling_cursors, group_id_aliases и onboarding_candidates, а также случайный request_id в onboarding_selections. В схеме 0002 им были созданы неиспользуемые serial-счётчики; их отставание от внешнего ID не означает потерю данных. Настоящие счётчики новых записей и последовательности неизвестных таблиц продолжают проверяться. Инструмент не меняет значения последовательностей.

## Возврат восстановленной БД в работу

Дамп отражает прошлое; Telegram мог выполнить действия после его создания. Сразу запускать восстановленную очередь нельзя.

1. Остановить все receiver. Сохранить повреждённую/текущую БД отдельно, если доступна. Восстановить и проверить выбранную копию в новую БД.
2. Указать новую БД явно в `ANTISCAM_MIGRATION_DATABASE_URL`, затем выполнить:

```sh
.venv/bin/python -m ops.recovery --quarantine-restored-work --expected-database antiscam_restore_recovery
```

3. Инструмент включает системную паузу, отменяет ещё не отправленные внешние операции и помечает бывшие `in_flight` неизвестными. Исходные решения, списки и история сохраняются. Он не обращается к Telegram.
4. Начать с `RECOVERY_MODE=true`. Сверить ограничения известных пользователей чтением Telegram и восстановить пропущенный интервал из доступных данных. Не переотправлять неизвестные удаления/уведомления. Данные, созданные после snapshot, требуют отдельного восстановления; отчёт не обещает нулевую потерю этого интервала.
5. После сверки переключить `RECOVERY_MODE=false`, перезапустить единственный receiver и отдельно подтвердить возобновление автосанкций владельцем. Старые отменённые задания автоматически не возобновляются.

## Что фиксировать в выпускном протоколе

Коммит/хеш файлов, версии окружения, время последнего старого update и первого V2 update, SHA-256 архива, отчёты миграции и восстановления, численные инварианты, проверку обеих групп и ролей, фактические RPO/RTO, 24-часовое наблюдение. Для непроверенного пункта писать «не проверено», не «пройдено».
